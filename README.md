# Negev

Negev is an early, self-hosted anime request and acquisition prototype. Its account-backed page can search AniDB titles through Shoko and record series and movie requests in a **held** state. It cannot acquire, import, or report live availability yet; the end-user pages remain an early preview.

A bounded read-only Shoko AniDB relation adapter and pure graph can collect verified prequels, sequels, side stories, films and alternative versions while leaving each AniDB installment separately requestable. Missing relation rows, unverified links and asymmetric edges hold the group. Shared-character and unexplained `Other` links do not merge it. Shoko's per-title endpoint returns outgoing relations only, so even a closed graph is labelled a related-installment candidate, not a complete franchise. It is not yet persisted, scheduled, connected to the account page, or proved against installed Shoko relation responses.

The account page can now request one title's verified direct relationships on demand and show their names. Each related title opens its exact AniDB ID, preserving installment-level requests even when titles share a name. It explicitly says the list may be incomplete. This view has synthetic tests only and does not use the transitive graph yet.

An optional `NEGEV_SHOKO_EVENTS=1` account-server setting connects to Shoko's supported SignalR `file` feed. It starts disabled, requires a confirmed subscription, bounds file-ID rechecks, and records gaps for later reconciliation. Detection events have no file ID; this feed alone does not prove Plex availability or perform a full reconciliation. The installed subscription and real import timing still need a controlled test before enabling it on the NAS.

An independent `NEGEV_SHOKO_INVENTORY=1` setting opts into paced read-only reconciliation: one page of 25 Shoko files per minute, a 24-hour rest after a complete pass, and a five-minute retry after an error. The SQLite cursor survives restart. Both observer flags remain off by default; the inventory records positive identities only and cannot claim a missing file was deleted. Neither observer starts downloads or reports Plex availability.

`NEGEV_AIRING_WATCH=1` opts into the account service's existing bounded AniDB Airing-watch poll, with at most three saved watches per page and one minute between pages. It requires `NEGEV_TIME_ZONE` (for example `Australia/Sydney`) so the current episode cutoff follows the owner's local calendar day. The saved request cursor survives restart. This only appends newly aired exact episode targets or closes a confirmed Completed watch; it does not search indexers or start downloads. It remains off by default and needs installed AniDB date-field validation before enabling.

For a whole-installment Airing request, Negev initially saves only regular episodes with a valid air date on or before that local day. It keeps the watch open for later AniDB episodes. A title with no aired regular episode holds until one is listed; a Completed request remains a one-time target set. A title that later becomes restricted holds its Airing watch without blocking other watches.

The gate calculates a completed video's ED2K hash, calls Shoko's read-only AniDB release-preview endpoint, and evaluates the response against its exact file size, AniDB file registration, anime ID, and requested episode IDs. An uncertain or incorrect result does not authorize import. In particular, Shoko's HTTP 204 response is inconclusive because its provider can also return 204 during an AniDB ban. The adapter is tested with fake responses only; it has not been connected to a live Negev service.

Run `pnpm install --frozen-lockfile` and `node --test` using Node.js 24. Tests use synthetic responses and make no live server calls.

## Intended boundaries

- Series and movies are independently requestable installments grouped by franchise.
- Every video accepted for import must match an AniDB-registered file and the requested anime/episode identity.
- Airing requests can monitor future episodes; completed requests are one-time acquisitions.
- Shoko and public Plex remain the authorities for final imported identity and playback availability.
- Direct Shoko imports must update availability without creating a Negev request.
- Negev must not expose incomplete downloads to Shoko or Plex.

The staging path guard checks regular video files inside an app-owned directory, rejects path escapes and symlinks, then performs the read-only identity check. A separate pure qBittorrent v5 evaluator checks torrent ownership, completion, selected files, and the staging save path. It accepts complete selected video and subtitle files under the same path policy as the stopped gate, while holding executable or unexpected files even if excluded. These pieces are not yet wired to a live qBittorrent session and do not move a file.
A narrow read-only qBittorrent adapter can now observe one expected torrent, its storage paths, and its file list twice before invoking that evaluator. It holds completion when qBittorrent's final or incomplete path is outside the isolated staging directory or changes between observations. It has synthetic tests only, no configured/live qBittorrent session, and cannot start or alter a download. A later worker must also verify every selected video's exact AniDB file identity before Shoko sees it.
A diagnostic batch verifier now joins those checks: it requires the observed torrent and saved acquisition attempt to match the request, verifies exactly the attempt's reserved episode subset against AniDB file identity, rejects an incomplete or over-budget pack, and rechecks the torrent afterward. A request can use multiple disjoint releases; one release cannot quietly claim the rest of the request. It reports evidence only (`handoffReady: false`). Its integration test uses tiny synthetic files; there is no live hashing, import, or media movement.
The lower-level staged file check also applies a per-file byte ceiling before hashing. These ceilings prevent accidental unbounded reads, but the current JavaScript ED2K implementation still needs CPU and disk load measurement and production throttling before use on the NAS.
Staged ED2K verification now shares a bounded average read-rate pacer across all files in a batch (16 MiB/s default) and yields between hash chunks. This does not cap the synchronous CPU burst within a chunk; a live worker still needs CPU limits and a measured NAS pilot.

A private Fastify service searches Shoko's AniDB title cache and reads cached AniDB episode detail. An unowned title with no detail row stays **details pending**. The explicit detail-load action requires a recent successful search hit, reads bounded episode pages, reserves a durable SQLite claim, and submits at most one metadata refresh. Catalogue GETs remain read-only. A refresh response never proves detail is complete, and uncertain submissions remain held.

A pure request-intent planner selects exact AniDB episodes from complete detail. Airing whole-installment requests mark future regular episodes for monitoring; Completed requests are one-time; explicit Specials do not add the rest of the installment. A private request route now combines complete Shoko detail, date-based release-state inference, the planner, and a durable ledger. It rejects client-supplied requester/status fields and holds restricted, unknown, or incomplete titles. Its single test requester is **not** an end-user account system, and nothing consumes the saved requests for acquisition yet.

The SQLite request ledger preserves exact intent across restarts. A submission key makes retries idempotent without preventing a later request for the same scope. Its schema keeps separate user histories while sharing exact AniDB episode targets. Every record remains held for availability evidence. The ledgers use Node 24's release-candidate `node:sqlite` API, which needs production review.

A pure availability evaluator accepts normalized, complete Shoko and Plex observations. It counts an episode Available only when an exact AniDB anime/episode file has a readable media part in an allowed **public** Plex library. A Shoko-only file waits for Plex; a private/test Plex part does not count; observer outages become Unknown. A low-level physical Part witness compares one Shoko path with one Plex path through explicit read-only mounts. It checks scoped canonical roots, device/inode/size, stability and a one-byte read through Plex, returning a shared storage key only for the same physical file. A bounded reader can fetch one known Plex episode or movie rating key and validate its type, public library identity and file Parts. Neither component scans a library or hashes media. Plex key discovery and verified container-path mappings are still needed before the evaluator can report production availability.
An isolated known-card join now combines the Shoko episode reader, Plex item reader and physical Part witness under an explicit 64-comparison default budget. It can prove a positive public episode match even if another Plex version is stale. Wrong files, private libraries, partial episodes and conflicting Shoko identities cannot say Available; missing cards and unreadable only versions stay Unknown. This join accepts only supplied observations and explicit mount translations. It does not discover every Plex card, prove absence, drive a download, or run on the NAS. Live response samples and current read-only mount proof remain required before operational use.

A bounded target observer composes one exact Shoko episode read with at most ten scoped public Plex card reads for either a series episode or a movie. It passes their Parts to the physical same-file join. One verified public card can establish positive availability despite another stale card; a missing, unreadable or incomplete card selection cannot establish absence. The account service can use it when explicitly enabled, but installed response proof and live arrivals are still required.

The join also checks card identity. A native Anime episode card must carry the exact Shoko episode and parent-series GUIDs from the AniDB episode response. A true Plex Movie card must carry the one exact TMDB movie ID linked by that Shoko episode, either as its primary or external GUID. A readable Part filed under a different show or episode stays Unknown. These rules are tested synthetically; installed Plex GUID fields and movie representation still require live read-only validation.

A positive-only Plex card index and explicit page worker retain scoped candidate Parts and a restart-safe page cursor in SQLite. One paced tick reads at most five cards plus one due retry; a transient card error cannot stall the wider sweep. A target observer uses fresh Shoko file sizes to select at most ten candidate cards, re-reads each card, and requires physical same-file proof before returning Available. The account route and optional scheduler are source-wired and off on the NAS. An index sweep cannot prove absence.

An isolated service composes installed-shape Shoko and Plex HTTP readers with that durable index. Its synthetic direct-import integration test starts Unknown before a public Plex card is indexed and becomes Available only when the exact Shoko release and a readable public Plex Part resolve to the same file. An opt-in exact-GUID probe can select candidate cards before the paced index reaches them; it still re-reads the card and proves physical identity. A saved live Plex test established the show-GUID filter on one section, but episode and movie GUID filters have not been checked against the installed server. The probe therefore remains disabled by default. No production account server has Plex credentials or mounts from Negev, and no genuine Negev arrival has been observed.

The account service hosts this observer only when `NEGEV_PLEX_OBSERVER=1` is configured with an explicit Plex URL, public section IDs, scoped read-only media mount mappings, and a restricted `/data/secrets/plex.token` file. The token is not accepted as a Docker environment variable. Its authenticated, rate-limited episode routes return only Available or Unknown, without internal file IDs or paths. `NEGEV_PLEX_INDEX=1` opts into a single-flight scheduler after one minute: one section page of at most five cards per minute, round-robin across configured sections, with each section's newest page revisited every tenth visit. `NEGEV_PLEX_GUID_PROBE=1` separately opts into exact-GUID candidate lookup for at most four configured public sections; it requires installed episode/movie filter proof before NAS use. All Plex switches remain off on the NAS. The actual mounts and response fields remain unverified.

The positive join accepts several explicit, non-overlapping Plex path mappings, which matters when public Anime Parts arrive through different VFS roots. It checks the selected mapped file against the Shoko source, including a Linux symlink-backed Part test. Unmapped or overlapping roots fail closed. The installed public library roots and the corresponding read-only Negev mounts still need to be verified before this is operational.
An optional private diagnostic route can now read one bounded key page from an explicitly allowlisted Plex library: `GET /api/availability/plex/keys?kind=episode&libraryId=1&offset=0`. It requires `NEGEV_PLEX_URL`, `NEGEV_PLEX_TOKEN`, and `NEGEV_PLEX_SECTIONS` (for example `episode:1,movie:2`) together. Without those settings the route returns unavailable. The reader first fetches the section's advertised type pivot and accepts only a same-server, same-section movie or episode `all` link; it does not construct a type link from an assumed path. The response contains rating keys only and always says `complete: false`; it does not expose file paths, scan more than one page, or imply that missing keys mean missing media. The installed Plex response shape and durable discovery across paging shifts still require verification before any operational observer uses it.
A bounded, read-only Shoko adapter can request one AniDB episode with its files, saved AniDB release data, and locations. It retains all accessible locations and verifies the saved release's exact AniDB anime, episode, file ID, ED2K, size, and episode coverage. A missing local Shoko episode stays distinct from a proven absence. An unregistered or malformed file makes the episode observation incomplete, while another independently verified file can still establish positive availability through a readable public Plex Part. Incomplete evidence cannot establish absence or complete a handoff. The adapter is tested against the published Shoko API shape, not yet against a real mixed-file episode on the installed server.

The Dockerfile defaults to the account-backed API. It requires explicit `NEGEV_USER_SERVER=1`, an absolute private `NEGEV_DATA_DIR`, Shoko URL, `NEGEV_SHOKO_API_KEY_FILE` at `<dataDir>/secrets/shoko.token`, and `NEGEV_PUBLIC_ORIGIN`; it fails closed otherwise. The account server rejects a Shoko key supplied in Docker environment variables and reads only a regular restricted token file beneath its private data mount. Initialize one admin offline with `NEGEV_ADMIN_USERNAME` and a password piped to `node src/auth/init-admin.mjs` through stdin, using the same private data volume. This creates a 32-byte session key and SQLite account database without storing the password in an environment variable. The listener binds loopback by default; all-interface binding requires `NEGEV_EXPOSE_USERS=1` and an HTTPS public origin. The old private diagnostic remains available by explicitly running `node src/web/private-server.mjs` with its separate private-test settings. GitHub CI builds and smoke-tests the account-backed image with synthetic settings and no external network; it does not publish or deploy the image.

A pure release-state helper infers Airing, Completed, Upcoming or Unknown from AniDB start/end dates and regular episode dates. Its result is labelled **inferred** because AniDB cannot reliably distinguish a hiatus or cancellation from an ongoing release. The opt-in account Airing worker uses it to extend saved requests, but the installed Shoko API date fields still need a read-only check. No download follows this poll.

The durable request ledger can now page active Airing watches and append newly listed, already aired regular AniDB episode IDs in transactions of at most 25 targets. It leaves future or unknown-date episodes deferred, never adds Specials, preserves the original submission key for idempotent retries, and holds if a complete catalogue snapshot loses an already linked episode. A trusted Completed observation appends remaining regular episodes in bounded batches and then closes that watch without changing Completed requests. No scheduled watcher or trusted live release-state source is connected yet; this storage behavior alone does not start a download.

An explicitly invoked private service method can poll up to three Airing requests at a time. It reads complete cached Shoko detail serially, shares one read for users watching the same installment, paces extra metadata pages, and lets one unavailable title hold while later requests advance. Episode-count inference alone leaves monitoring open; an explicit past end date with consistent episode dates may close it. A durable page cursor continues through later requests after restart. The private diagnostic can opt into a timer with `NEGEV_PRIVATE_AIRING_POLL=1`: it waits one minute before the first page, ten seconds between pages, one hour after a full pass, and five minutes after a failed poll. The timer stops and drains before SQLite closes. The installed Shoko date-field contract is still unverified; this timer has no download action and is not an operational end-user worker.

An account-backed HTTP boundary is now separate from the private diagnostic. Its durable account ledger bootstraps one admin offline, stores scrypt password hashes, issues one-use invitations for members, and revokes old sessions by version. The Fastify boundary uses encrypted cookies, an exact Origin and CSRF check for writes, login throttling, server-derived requester IDs, and per-user request reads. The API also wires authenticated catalogue search, detail hydration, held series/movie requests and owner-scoped, bounded request-history pages to real SQLite. A guarded listener, bootstrap CLI, and a small first page exist, but there is no production deployment. The page uses text-only AniDB results because the installed title cache does not establish artwork for unowned titles. It clearly labels saved requests as not acquiring yet. The private test bearer token is not an account credential.

The account-backed service admits only one Shoko metadata operation at a time across search, detail, hydration and request planning. Concurrent calls return a retryable busy response rather than queuing a backlog. Request submission is limited to five attempts per minute per client address, and detail reads to ten per minute. This is an instance-local load cap for one container, not a distributed quota or proof that the installed Shoko server can tolerate the configured page budget.

The full end-user UI, operational indexer/qBittorrent workflow, automatic Shoko handoff, and live Plex observation are **not implemented**. The acquisition modules are not connected to a route or worker. No production service has been changed for this repository.

A read-only Prowlarr search adapter can return bounded, sanitized torrent **candidates** from configured indexers. The guarded diagnostic offers `GET /api/releases/search?q=...` only when `NEGEV_PROWLARR_URL`, `NEGEV_PROWLARR_API_KEY`, and comma-separated `NEGEV_PROWLARR_INDEXER_IDS` are all configured. This free-text route uses the private bearer token and does not inspect saved requests. The search cannot grab a release. Even a successful empty search does not prove that no release exists. Candidate titles do not satisfy Negev's exact AniDB-file requirement.
A second private GET route, `/api/requests/:id/candidates`, joins an existing held request to current complete Shoko detail, verifies its AniDB show and episode IDs again, and searches Prowlarr using Shoko's canonical title. Both paths are diagnostic only: they do not select, download or import anything, and no release is treated as an exact file match.
A separate SQLite acquisition ledger requires each candidate to claim an explicit subset of the saved request's exact episode targets, binds the prepared torrent hash to that candidate, and records a one-time dispatch intent before any external call. Overlapping target episodes or an identical torrent hash cannot be claimed twice; unrelated episodes can continue. An uncertain dispatch remains held across restarts instead of triggering another grab. A candidate may release its claims only while still unbound and unsent; its old identity cannot be reused after release. Bound or sent attempts remain held until an evidence-based completion or failure policy is implemented. The ledger is not wired into the private routes and does not mark requests fulfilled. A worker must prove each selected target is still missing before reserving it.

A server-side coordinator now composes Prowlarr torrent-byte preflight, a fresh exact missing-target snapshot, durable reservation of one explicitly selected episode subset, and the guarded one-send stopped qBittorrent submission. It holds on a present target, provider outage or unsafe staging mount; replay of an observed stopped torrent does not add it again. This is a controlled-acquisition building block with synthetic provider tests, not automatic candidate selection or a running worker. It has no route and cannot start a torrent, verify downloaded files, import into Shoko or report availability.
The coordinator also checks every proposed video filename and size against the torrent metainfo, requires the proposal to cover exactly its claimed episode subset, and stores that provisional filename-to-episode plan beside the attempt in SQLite. A restart can recover the same plan; a changed assignment cannot replace it. This is a pre-download plan only. AniDB's exact registered-file identity and full episode coverage must still be verified after the video bytes finish downloading.
The recorded-batch verifier now reloads the saved request, torrent attempt, start intent and file plan before calling the staged byte verifier. It holds before reading media if the plan or start intent is missing, and it rejects a completed file whose size differs from the saved torrent plan. This is still a private building block: a live worker and installed qBittorrent/Shoko observations are required before it can report an accepted import.

The first reservation coordinator now requires one fresh, complete Shoko and public Plex observation for the selected episode subset. It reserves only when every selected episode is proven absent; a playable episode, a Shoko file awaiting Plex, partial coverage, an observer outage, or stale evidence holds the whole candidate. This is tested with real SQLite ledgers and synthetic observations. No live observer supplies this snapshot yet, and no app route or worker invokes the coordinator.

A separate pure form builder prepares **one torrent file** for qBittorrent's add API with the fixed `/negev-staging` destination, `negev` category, `stopped=true`, and automatic torrent management disabled. It makes no HTTP call. The destination is only a proposed container mount name: it does not yet exist on the NAS. Prowlarr's built-in qBittorrent client passes a category but does not set this explicit save path, so its grab route is not used for Negev staging.
A separate GET-only observer now reads a stopped torrent and its file list twice. It holds a changed, started, partially downloaded, wrong-owner, wrong-path, malformed, or oversized manifest. The pure evaluator permits selected videos and subtitles; passive extras must be excluded, and all other file types hold even if excluded. This is a file-list safety gate, **not** proof that any video is registered in AniDB. It cannot start or import a torrent, and has only synthetic tests.
A server-only Prowlarr reader can now re-search one selected torrent candidate and retrieve its torrent bytes through Prowlarr's proxy. It requires the same GUID, indexer, title and size, a same-origin proxy URL with exact path/authentication parameters, no redirects, torrent content type, and a 2 MB byte cap. It returns bytes only to its caller; it does not expose the proxy URL to users or send anything to qBittorrent. This path is not wired to an acquisition worker and has only synthetic tests. Indexers configured to redirect instead of proxy are held.
An independent torrent-metainfo preflight parses bounded canonical bencoding, validates v1/v2/hybrid file paths and sizes, compares hybrid file views, and derives the qBittorrent torrent ID from the raw `info` bytes. It does not validate downloaded piece hashes or v2 Merkle layers and does not establish AniDB registration. A server-only coordinator joins the Prowlarr reader, preflight and qBittorrent add form, returning the exact expected hash and a stopped staging form. A separate low-level submitter can now validate that form, check mount evidence and host realpath, record one-time intent, post one stopped torrent, and reconcile an uncertain response against the exact stopped manifest. No route or scheduled worker invokes it, and it has only synthetic provider tests.

Do not commit credentials, NAS configuration, database copies, logs, operational evidence, or media to this public project.

The account-backed service joins authenticated AniDB search and detail reads to held series and movie requests in one durable SQLite database. It uses the same exact request-key retry before catalogue admission, so a saved request remains recoverable after a restart or catalogue outage. Catalogue hydration writes Shoko metadata and is disabled by default; it requires the separate `NEGEV_SHOKO_HYDRATION=1` setting after its operational use is approved. The Docker image starts this account-backed API when explicitly configured. The account server can opt into read-only operator release discovery with `NEGEV_PROWLARR_DISCOVERY=1`, a same-origin `NEGEV_PROWLARR_URL`, `NEGEV_PROWLARR_INDEXERS` as a JSON array of allowed numeric indexer IDs, and `NEGEV_PROWLARR_KEY_FILE` fixed to `<dataDir>/secrets/prowlarr.token`. The key is rejected in Docker environment variables. Only an admin sees the on-demand “Review release candidates” control for a saved request. It rechecks that request's current AniDB title and exact targets before searching, labels every result unverified, and never adds or starts a torrent. An admin can inspect one discovered candidate's torrent metadata through `POST /api/requests/:id/preflight`. The stopped-torrent submitter can now exclude known passive artwork and note files with qBittorrent's supported `filePrio=0` action, but only after double-observing a pristine stopped Negev torrent. It double-observes the manifest again and records the torrent only when the passive files are excluded and the selected videos remain safe. Executable, archive, script and unsafe paths still hold without a priority write or torrent start. The admin preflight labels these extras as planned exclusions; it does not perform the write. Before any file-priority change or stopped-manifest acceptance, Negev also compares every qBittorrent file name and size with the original torrent metainfo. A pure staging-mount check evaluates Docker inspect `Mounts` arrays for qBittorrent, Shoko and Plex. It requires one writable `/negev-staging` bind from the configured host directory, rejects nested qBittorrent mounts, and rejects any Shoko or Plex mount that covers it. The low-level submitter also requires an exact host realpath. A separate low-level start gate repeats that isolation proof and the double stopped-manifest check, records one durable start intent, then sends one exact-hash `torrents/start` POST. The handoff preparation module can copy a previously AniDB-verified batch into a private, unwatched holding directory. Selected subtitle sidecars are limited to 16 MiB each and 64 MiB per batch, SHA-256 hashed, and copied with the verified videos; a changed sidecar holds the entire batch. This local building block is not wired to a worker or live NAS mounts, and its result explicitly does not authorize publication into Shoko Import. Before operational use, Negev still needs fresh mount and free-space proof, durable handoff integration, a fresh completion and identity check, and an atomic whole-batch publish into Shoko's watched source.

A separate SQLite handoff ledger now binds a prepared batch's video/subtitle evidence digest and torrent hash to its acquisition attempt, exact reserved episode subset and private holding path.
