# Durable acquisition attempt boundary

The request ledger owns user history and exact AniDB episode targets. A separate SQLite acquisition ledger reserves one candidate for an existing held request and claims only its target episodes. A competing candidate for an overlapping episode is held; unrelated episodes remain free. The raw Prowlarr GUID is hashed before storage, so torrent URLs or indexer tokens are not persisted in this table.

After preparing the exact torrent bytes, the worker must bind their derived qBittorrent hash to the reserved candidate with `bindPreparedTorrent`. The binding checks the saved candidate digest and indexer, and persists the hash. `beginDispatch` refuses an unbound attempt; once bound, it durably changes the attempt to `dispatch_unknown` and grants one send action. A restart or repeated call returns `sendNow: false`; it must reconcile qBittorrent before acting again. Only that exact expected hash can be recorded as observed. Older diagnostic attempts without a bound hash stay unsendable after schema migration. Tests exercise restart, migration and two SQLite connections against temporary databases.

This is a data boundary, not a dispatcher. It never calls Prowlarr or qBittorrent, releases a target claim, retries a failed candidate, verifies a torrent, or marks a request fulfilled. A later controlled workflow must check current Shoko/Plex availability before reservation, prove the isolated staging mount, submit the stopped torrent at most once, bind the observation to the configured Negev category and staging path, and define cleanup evidence before releasing a held target for another candidate. Node 24's `node:sqlite` support status remains a production packaging review item.
